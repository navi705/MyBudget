# Техническое видение проекта "MyBudget"

Этот документ описывает два альтернативных подхода к технической реализации проекта, основанных на разных технологических стеках. Цель — сравнить их плюсы и минусы в контексте требований, изложенных в `idea.md`.

## 1. Общие принципы и подходы

Следующие принципы являются общими для обоих вариантов:

*   **Принцип разработки:** GitFlow в качестве модели ветвления. CI/CD на базе GitHub Actions для автоматической сборки, тестирования и деплоя.
*   **Структура проекта:** Монорепозиторий (Monorepo) для хранения кода всех компонентов (клиентов, бэкенда), чтобы упростить управление зависимостями и сквозные изменения.
*   **Архитектура проекта:** Применение принципов **Чистой Архитектуры (Clean Architecture)**. Это позволит изолировать бизнес-логику от фреймворков и деталей реализации (UI, база данных), что критически важно для поддержки нескольких моделей развертывания и долгосрочного развития.
*   **Модель данных:** Основные сущности: `User`, `Account` (счет), `Transaction`, `Category` (древовидная), `Currency`, `Goal` (цель), `InvestmentAsset`, `ForecastSnapshot`.
*   **Деплой:**
    *   **Self-Hosted:** Упаковка бэкенда и БД в Docker-контейнеры, распространяемые через Docker Hub. Установка с помощью `docker-compose`.
    *   **SaaS:** Развертывание Docker-контейнеров в кластере Kubernetes для масштабируемости и отказоустойчивости.
*   **Логирование:** Структурированное логирование в формате JSON. В Docker-режиме — вывод в `stdout`. В облаке — сбор логов агрегаторами (например, ELK Stack, Datadog).
*   **Конфигурирование:** Управление конфигурацией через переменные окружения, согласно принципам 12-Factor App.
*   **Тестирование:**
    *   **Unit-тесты:** Покрытие основной бизнес-логики.
    *   **Интеграционные тесты:** Проверка взаимодействия с реальной базой данных (запускаемой в Docker).
    *   **E2E-тесты:** Сквозное тестирование пользовательских сценариев.
    *   **Mock-сервер:** Использование mock-сервера (например, WireMock) для автономного тестирования клиентских приложений без реального бэкенда.
*   **Мониторинг:** Сбор метрик с помощью Prometheus и визуализация в Grafana.

## Вариант А: Стек "Cloud-Native & Cross-Platform" (Рекомендация Gemini)

Этот стек ориентирован на максимальную производительность, низкое потребление ресурсов и унификацию кодовой базы.

### 1. Технологии
*   **Клиентские приложения (Web, Desktop, Mobile):** **Flutter (язык Dart)**. Единая кодовая база для всех платформ.
*   **Бэкенд:** **Go (Golang)** с использованием легковесного фреймворка (например, Gin или Echo).
*   **База данных (серверная):** **PostgreSQL**.
*   **База данных (локальная, для P2P):** **SQLite**.

### 2. Преимущества
*   **Скорость и стоимость разработки:** Единая кодовая база клиента радикально ускоряет и удешевляет разработку и поддержку.
*   **Консистентность UI:** Flutter обеспечивает идентичный внешний вид и поведение на всех платформах.
*   **Производительность и ресурсы:** Go — один из самых быстрых языков для API с минимальным потреблением памяти. Идеально для SaaS и self-hosting на слабом "железе".
*   **Простота деплоя:** Бэкенд на Go компилируется в один маленький статический файл, что упрощает создание Docker-образа.

### 3. Недостатки
*   **Новый стек:** Требует изучения Flutter/Dart и Go, если нет соответствующего опыта.

## Вариант Б: Стек "Enterprise .NET & Native" (Привычный вам)

Этот стек опирается на зрелую, мощную экосистему Microsoft и классический нативный подход к разработке UI.

### 1. Технологии
*   **Клиентские приложения:** Нативная разработка для каждой платформы.
    *   **Windows:** **WinUI 3** (C#).
    *   **Android:** **Kotlin/Jetpack Compose**.
    *   **Web:** **Blazor** или **React/Angular** (TypeScript).
    *   **Будущие платформы:** Swift/SwiftUI (iOS/macOS), Avalonia (Linux).
*   **Бэкенд:** **ASP.NET Core (C#)**.
*   **База данных (серверная):** **PostgreSQL** (или MS SQL Server) с использованием ORM **Entity Framework Core**.
*   **База данных (локальная, для P2P):** **SQLite** (также через Entity Framework Core).

### 2. Преимущества
*   **Привычные инструменты:** Использование знакомой и мощной экосистемы .NET и C#.
*   **Максимально нативный UX:** Каждое приложение будет на 100% "родным" для своей платформы.
*   **Скорость разработки бэкенда:** ASP.NET Core и EF Core предоставляют множество инструментов "из коробки", ускоряя создание API.

### 3. Недостатки
*   **Стоимость и сложность разработки UI:** Необходимость поддерживать 3+ отдельных клиентских проекта. Разработка и тестирование каждой фичи занимает в разы больше времени и ресурсов.
*   **Проблемы консистентности:** Сложность в обеспечении одинакового вида и поведения на разных платформах.
*   **Больший размер Docker-образа:** Бэкенд на ASP.NET Core требует наличия .NET Runtime и имеет больший размер, что делает его менее удобным для self-hosting.

## 2. Дополнительные аспекты видения

### 2.1. Безопасность (Security)

*   **Аутентификация:** Будет реализована гибридная модель:
    *   **Нативная:** Регистрация по email/паролю с хранением хэшированных паролей (алгоритм bcrypt).
    *   **OAuth 2.0:** Вход через аккаунты Google. В будущем возможно добавление других провайдеров.
*   **Шифрование данных:**
    *   **В пути (In-Transit):** Весь трафик между клиентом и сервером будет защищен с помощью TLS (HTTPS).
    *   **В покое (At-Rest):** Данные на сервере будут защищены с помощью встроенных механизмов шифрования PostgreSQL.
    *   **P2P-режим:** Локальный файл базы данных SQLite будет **обязательно шифроваться**. Доступ к данным будет осуществляться по мастер-паролю, по аналогии с менеджерами паролей KeePass.
*   **Безопасность API:** Бэкенд будет разрабатываться с учетом лучших практик для защиты от угроз из списка **OWASP Top 10**.
*   **Анализ зависимостей:** Будет настроен **GitHub Dependabot** для автоматического сканирования проекта на наличие уязвимых библиотек.

### 2.2. Стратегия Open Source

*   **Лицензия:** Проект распространяется под лицензией **Apache License 2.0**.
*   **Управление проектом:** На начальном этапе для баг-репортов и предложений по функциям будет достаточно **GitHub Issues**.

### 2.3. API и интеграции

*   **Дизайн API:** На первом этапе будет использоваться **REST API**.
*   **Версионирование API:** Применяется лучшая практика версионирования через URL. Например, `/api/v1/transactions`. Это позволяет безболезненно вносить изменения в API, не ломая старые клиенты.

### 2.4. Сборка и артефакты

*   **CI/CD:** Весь процесс автоматической сборки, тестирования и публикации будет построен на **GitHub Actions**.
*   **Хранение артефактов:** Собранные Docker-образы и клиентские приложения будут публиковаться в **GitHub Packages**.
*   **Локальная разработка:** Процесс сборки и запуска будет полностью документирован для возможности локальной разработки и тестирования.

### 2.5. Документация

*   **Подход:** Документация — неотъемлемая часть проекта.
*   **Типы документации:**
    *   **Для пользователей:** Руководства и описание функций.
    *   **Для разработчиков:** Описание архитектуры, API, инструкции по настройке.
    *   **Внутрикодовая документация:** В каждой значимой папке с исходным кодом будет находиться файл `README.md`, описывающий назначение этого модуля/компонента.

### 2.6. Интернационализация (i18n) и Локализация (l10n)

*   **Подход:** Проект с самого начала будет проектироваться с учетом поддержки нескольких языков.
*   **Реализация:** Весь пользовательский текст (в UI, в уведомлениях и т.д.) будет вынесен в отдельные файлы ресурсов. Это позволит легко добавлять новые языки в будущем, не изменяя исходный код приложения.

### 2.7. Архитектура плагинов и расширяемость

*   **Философия:** Приложение должно быть не монолитом, а платформой, функциональность которой можно расширять с помощью плагинов. Это позволит как нам, так и сообществу, легко добавлять новые возможности.
*   **Точки расширения:** Плагины могут быть созданы для следующих областей:
    *   **Импорт данных:** Создание парсеров для банковских выписок, SMS, или API конкретных банков.
    *   **Источники данных:** Плагины для получения курсов валют или данных по инфляции из различных источников.
    *   **Темы и кастомизация:** Добавление новых тем оформления и наборов иконок.
    *   **Отчеты:** Создание новых типов отчетов и виджетов для дашборда.
*   **Реализация:** Архитектура будет определять четкие **интерфейсы (контракты)** для каждой точки расширения. Плагин — это, по сути, реализация такого интерфейса. Например, для импорта данных будет существовать интерфейс `IDataImporter`, и любой плагин должен будет предоставить класс, реализующий его методы.

### 2.8. Принципы качества кода

Для достижения необходимой гибкости, расширяемости и поддерживаемости, код проекта будет строго следовать общепринятым принципам проектирования:

*   **SOLID:** Да, принципы SOLID абсолютно актуальны и являются основой нашей архитектуры.
    *   **S (Принцип единственной ответственности):** Каждый компонент выполняет одну задачу.
    *   **O (Принцип открытости/закрытости):** Система открыта для расширения (через плагины), но закрыта для модификации существующего, работающего кода.
    *   **L (Принцип подстановки Барбары Лисков):** Обеспечивает корректную работу полиморфизма в нашей системе плагинов.
    *   **I (Принцип разделения интерфейса):** Плагины зависят только от тех интерфейсов, которые им действительно нужны.
    *   **D (Принцип инверсии зависимостей):** Является ядром выбранной нами Чистой Архитектуры, позволяя бизнес-логике не зависеть от деталей реализации.
*   **DRY (Don't Repeat Yourself):** Избегание дублирования кода для упрощения поддержки.
*   **KISS (Keep It Simple, Stupid):** Предпочтение простых и ясных решений сложным и запутанным.
