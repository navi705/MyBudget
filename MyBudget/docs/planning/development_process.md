# Процесс разработки и стандарты проекта

Этот документ — набор инструкций и правил для меня, Gemini, для обеспечения качества и консистентности кода.

## 1. Цикл разработки

### 1.1. Git Flow
Я буду строго придерживаться модели Git Flow:
*   **`main`**: Содержит только стабильные, релизные версии.
*   **`develop`**: Основная ветка разработки. Все feature-ветки вливаются сюда.
*   **`feature/<описание>`**: Вся новая работа ведется в таких ветках. Ветвь создается от `develop`.
*   **Pull Requests (PRs)**: По завершении работы в feature-ветке, я создам Pull Request в `develop`. В PR я предоставлю краткое описание проделанной работы.

### 1.2. Коммиты
Я буду использовать стандарт **Conventional Commits**. Коммиты должны быть атомарными и представлять собой **логически завершенный, работающий фрагмент**. Не следует делать коммиты с пустыми файлами или папками.
*   **Формат:** `<тип>: <описание>`
*   **Основные типы:** `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.

## 2. Стандарты качества кода

### 2.1. Принципы проектирования
Я буду проектировать весь новый код, основываясь на принципах:
*   **SOLID**: Основа для гибкой и расширяемой архитектуры.
*   **DRY** (Don't Repeat Yourself).
*   **KISS** (Keep It Simple, Stupid).

### 2.2. Стиль и именование
*   **Форматирование:** Я буду автоматически применять `gofmt` для Go и `dart format` для Flutter перед каждым коммитом.
*   **Именование:** Я буду следовать соглашениям, описанным в `vision.md` (kebab-case для папок, snake_case для файлов, PascalCase для классов, camelCase для переменных/функций).
*   **Запрещено:** Я не буду оставлять в коде закомментированные участки, "магические" числа или игнорировать предупреждения линтера.

## 3. Стратегия тестирования

Я буду придерживаться поэтапного подхода к тестированию:

1.  **Unit-тесты:** При реализации новой бизнес-логики (например, в Domain Layer) я сначала напишу unit-тесты, которые проверяют все сценарии, а затем напишу код, который заставит эти тесты пройти.
2.  **Интеграционные тесты:** После реализации логики в слое данных (Data Layer), я напишу интеграционные тесты для проверки корректной работы с базой данных (создание, чтение, обновление, удаление).
3.  **E2E-тесты (End-to-End):** Для ключевых пользовательских сценариев (например, "добавить транзакцию и увидеть ее в списке") я буду создавать сквозные тесты, которые имитируют действия пользователя в UI.

## 4. План разработки и отчетность

*   **Источник задач:** Я буду использовать единый файл `TASKLIST.md` в папке `docs/planning`.
*   **Гранулярность задач:** Каждая задача в списке должна представлять собой **значимый, функциональный блок** (например, "Реализовать модуль аутентификации"), а не отдельное мелкое действие.
*   **Структура `TASKLIST.md`:**
    *   **Отчет о прогрессе:** Вверху файла будет находиться таблица с общим прогрессом по ключевым этапам. Я буду обновлять ее после завершения каждого этапа.
    *   **Детальный план:** Ниже будет идти пошаговый план разработки, где каждая крупная задача будет представлена в виде пункта с чекбоксом `[ ]`.
*   **Декомпозиция задачи:** Внутри каждой крупной задачи я по-прежнему буду следовать внутреннему под-плану (тесты, код, документация) и согласовывать с вами каждый шаг.
    *   **Декомпозиция задачи:** Для каждой задачи по реализации функционала я буду следовать внутреннему под-плану, строго придерживаясь цикла "Тест -> Код -> Запуск":
        1.  `[ ]` **Написание теста:** Я предложу код теста для новой функциональности.
        2.  `[ ]` **Запуск теста (Красный):** Я запущу тест и убежусь, что он проваливается (потому что функциональности еще нет).
        3.  `[ ]` **Реализация кода:** Я предложу код, необходимый для прохождения теста.
        4.  `[ ]` **Запуск теста (Зеленый):** Я запущу тест и убежусь, что он проходит.
        5.  `[ ]` **Рефакторинг:** Я предложу улучшения кода, если необходимо, и снова запущу тесты.
        6.  `[ ]` **Документация:** Написание или обновление соответствующей документации.
